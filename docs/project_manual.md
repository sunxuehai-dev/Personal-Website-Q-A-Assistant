# Resume Assistant 项目说明书

更新时间：2026-04-16
适用代码目录：`D:\newpycharmworkingspace\resume_assistant`

## 1. 项目定位

`Resume Assistant` 的目标不是做一个复杂的通用智能体平台，而是做成一个：

- 前后端分离思路清晰
- 可部署到小规格服务器
- 支持简单并发访问
- 具备问答助手常见核心模块
- 适合个人网站内嵌使用

的轻量问答系统。

当前硬件约束明确：

- 部署目标为 2 核 2G 阿里云轻量应用服务器
- 需要控制模型调用次数、请求耗时、上下文长度和服务复杂度

因此本项目的总原则是：

**麻雀虽小，五脏俱全；实现完整，但不做过重设计。**

## 2. 项目最终目标架构

项目最终目标架构定义为：

**前后端分离的轻量单体问答网站，后端内部采用模块化 QA 编排架构，支持短期会话记忆、本地 RAG、按需联网补充、流式输出和简单并发处理。**

这一定义包含四层：

1. 展示层
2. API 层
3. QA 编排层
4. 数据与基础设施层

### 2.1 展示层

负责：

- 个人主页展示
- 聊天界面
- 文件上传交互
- 会话状态显示

当前状态：

- 旧版模板主页仍保留在 `/`
- 新版独立前端已可通过 `/frontend` 访问

目标形态：

- 与后端通过 HTTP API / SSE 通信
- 前后端逻辑边界清晰
- 同仓库维护，按配置决定首页入口

### 2.2 API 层

负责：

- 对前端暴露稳定接口
- 请求校验
- 上传与会话状态管理
- 流式输出封装

目标形态：

- 保持 FastAPI 单体服务
- 统一处理 `/chat`、`/chat_stream`、上传、状态、会话相关接口

### 2.3 QA 编排层

负责：

- 问题理解
- 本地相关度判断
- 本地 RAG 检索
- 按需联网补充
- 最终回答生成
- 轻量重试
- 短期会话记忆承接

目标形态：

- 一个统一问答主链路
- 模块化组织，而不是多个独立助手互相竞争

### 2.4 数据与基础设施层

负责：

- 文件存储
- 向量库持久化
- 模型配置
- 部署配置
- 会话运行状态

目标形态：

- 文件系统 + Chroma + 轻量会话存储
- 不引入重型中间件

### 5.10 `app/retrieval/`：检索层

组成：

- `vectorstore.py`
- `retriever.py`
- `keyword.py`
- `hybrid.py`

职责：

- 构建和连接 Chroma 向量库
- 执行 dense retrieval
- 执行关键词检索
- 合并与去重证据

当前结构：

- `ResumeRetriever` 对应 `self_resume`
- `UploadedDocumentRetriever` 对应 `uploaded_docs`

设计意义：

- 本地 RAG 已经收敛成统一上下文增强层
- 不再走复杂的多分支显式路由

后续要求：

- 检索层只负责找证据，不负责最终回答
- 记忆模块不能和检索层混在一起

### 5.11 `app/agent/`：问答编排层

这是当前项目最重要的模块。

当前模块组成：

- `models.py`
- `router.py`
- `analysis.py`
- `planning.py`
- `synthesis.py`
- `evaluation.py`
- `rewrite.py`
- `service.py`

#### 5.11.1 `models.py`

职责：

- 定义问答编排中的数据结构

当前数据类包括：

- `RelevanceDecision`
- `QueryAnalysis`
- `RetrievalStep`
- `RetrievalPlan`
- `RetrievedEvidence`
- `RetrievalBundle`
- `AnswerDraft`
- `EvaluationDecision`
- `QAResponse`

作用：

- 让主链路各阶段的数据交互明确、可维护

#### 5.11.2 `router.py`

职责：

- 当前并非旧式路由器
- 实际承担 `LocalRelevanceJudge`
- 判断当前问题是否值得使用本地资料

输出：

- `high`
- `medium`
- `low`

作用：

- 避免所有问题都无脑走本地检索
- 为后续是否使用本地知识库提供前置判断

#### 5.11.3 `analysis.py`

职责：

- 判断任务类型
- 判断检索源范围
- 提取 query terms
- 判断是否需要关键词检索

当前支持的任务类型：

- `fact`
- `summary`
- `locate`
- `compare`

当前支持的 source scope：

- `self_resume`
- `uploaded_docs`
- `both`

后续演进重点：

- 会话记忆补全能力可继续在这里增强
- 用于处理追问补全和上下文承接

#### 5.11.4 `planning.py`

职责：

- 根据分析结果生成检索计划

当前策略：

- 单源问题走 `dense + 可选 keyword`
- 双源问题走平衡合并

作用：

- 把“怎么检索”从业务主流程中拆出来

#### 5.11.5 `synthesis.py`

职责：

- 使用统一提示词组织最终回答
- 对 Qwen 调用统一开启 `enable_search=true`
- 支持普通回答与流式回答

当前特点：

- Qwen 模式下按需联网补充
- 普通与流式回答复用同一思路
- 已注入最近对话上下文，改善连续追问表达

后续演进重点：

- 最终回答阶段要利用最近对话上下文

#### 5.11.6 `evaluation.py`

职责：

- 评估当前回答是否需要一次补救性重试

当前策略：

- 只允许一次轻量重试
- 根据本地相关度、检索质量和回答失败迹象决定

设计原则：

- 保持轻量，不引入复杂自反思链条

#### 5.11.7 `rewrite.py`

职责：

- 在重试时改写问题，扩大召回

作用：

- 在不增加太多复杂度的前提下提高容错率

#### 5.11.8 `service.py`

职责：

- 串起整个问答主链路

当前主流程：

```text
用户问题
-> SessionMemory 读取最近消息
-> 追问补全（effective question）
-> LocalRelevanceJudge
-> 可选本地检索
-> ResponseSynthesizer（携带最近对话上下文）
-> AnswerEvaluator
-> 必要时 RetryRewriter + 扩检索
-> 最终答案
-> SessionMemory 记录本轮问答
```

当前状态：

- 这是项目现阶段的核心业务内核
- 应继续保持为统一入口

后续演进重点：

- 继续控制链路长度，不扩展为重型多 Agent 结构

#### 5.11.9 已接入的会话记忆位置

当前第一版会话记忆已经实际接入：

- `app/agent/service.py`：读取最近消息、构造追问补全文本、在问答完成后写回本轮消息
- `app/agent/synthesis.py`：将最近对话上下文注入最终回答提示词
- `static/scripts/site.js`：生成并持有浏览器侧 `session_id`，支持清空当前会话

当前记忆形态仍然保持轻量：

- 仅进程内保存
- 仅保存最近几轮消息
- 仅服务当前浏览器会话连续追问

### 5.13 `app/memory/`：会话记忆层

组成：

- `models.py`
- `service.py`

职责：

- 按 `session_id` 保存最近几轮对话
- 识别简短追问并补足上下文
- 为最终回答阶段提供最近对话摘要
- 提供会话清空能力

当前实现特点：

- 采用进程内内存存储，不引入数据库
- 默认保留最近 `SESSION_MEMORY_MAX_TURNS` 轮
- 通过简单 follow-up heuristics 判断是否需要补全上下文

设计边界：

- 不是长期记忆
- 不是知识库
- 不做跨实例共享
- 服务重启后自然丢失

### 5.14 `app/runtime/`：运行时保护层

组成：

- `guards.py`

职责：

- 控制上传灌库互斥
- 控制聊天请求最大并发
- 为状态接口提供运行时快照

当前实现特点：

- 上传使用互斥锁保护
- 聊天使用信号量限制并发槽位
- 流式响应结束后自动释放聊天槽位

设计边界：

- 目标是小机器稳定，不是高并发扩展
- 当前保护范围仅限单进程内
- 后续如切多 worker，需要重新评估共享状态策略

### 5.15 错误响应与接口契约层

当前接口错误返回已统一采用兼容结构：

- `detail`：保留给旧逻辑和简单客户端使用
- `error.code`：稳定错误码
- `error.message`：面向前端的标准错误文本
- `error.retryable`：是否适合前端提示用户稍后重试
- `error.status_code`：HTTP 状态码镜像

当前已明确覆盖的典型错误码包括：

- `empty_question`
- `self_resume_missing`
- `unsupported_file_type`
- `upload_too_large`
- `upload_busy`
- `chat_capacity_full`
- `validation_failed`
- `model_timeout`
- `chat_failed`

这层的目标不是做复杂错误平台，而是保证：

- 前端提示稳定

## 6. 当前问答主链路架构

当前统一问答架构可表述为：

```text
用户问题
-> SessionMemory 读取最近消息
-> 追问补全（effective question）
-> LocalRelevanceJudge
-> QueryAnalyzer
-> RetrievalPlanner
-> Dense / Keyword Retrieval
-> Hybrid Merge
-> ResponseSynthesizer（携带 conversation context，Qwen 下 enable_search=true）
-> AnswerEvaluator
-> 必要时单次 RetryRewriter + 扩检索
-> 最终答案
-> SessionMemory 写回本轮问答
```

这条链路的原则是：

- 本地 RAG 是上下文增强，不是独立产品分支
- 联网能力由统一回答阶段按需触发
- 只允许一次轻量重试
- 回答体验优先采用流式输出

## 6.1 一次完整请求的生命周期

为了让后续维护者快速理解系统，这里按真实请求顺序描述一次完整问答过程。

### 6.1.1 前端发起请求

前端在浏览器侧完成这些准备：

- 读取或生成 `session_id`
- 根据当前是否存在上传文档决定 `use_uploaded_docs`
- 优先请求 `/chat_stream`
- 如果流式失败，则降级请求 `/chat`

### 6.1.2 API 层校验与准入

后端 API 层完成：

- 问题非空校验
- 自有简历知识库是否已准备完成校验
- 聊天并发槽位准入
- 异常统一转换为标准错误响应

### 6.1.3 会话记忆预处理

进入问答主链路后：

- 读取当前 `session_id` 最近几轮消息
- 判断当前问题是否像追问
- 必要时构造 `effective question`
- 同时保留面向最终回答提示词的 `conversation context`

### 6.1.4 本地相关度与检索规划

随后进入：

- `LocalRelevanceJudge`
- `QueryAnalyzer`
- `RetrievalPlanner`

这一步的目标是判断：

- 是否值得使用本地资料
- 应该检索 `self_resume`、`uploaded_docs` 还是两者一起
- 是否需要追加关键词检索

### 6.1.5 本地检索与证据融合

如果本地相关度不是 `low`，系统会执行：

- dense retrieval
- keyword retrieval
- hybrid merge

最终得到统一的本地证据集合 `evidences`。

### 6.1.6 最终回答生成

`ResponseSynthesizer` 负责：

- 把用户原问题、本地证据、最近对话上下文组织进提示词
- 在 Qwen 模式下统一开启 `enable_search=true`
- 生成普通回答或流式回答

### 6.1.7 轻量重试

如果 `AnswerEvaluator` 判断当前回答质量不理想，系统只会进行一次补救性重试：

- `RetryRewriter` 改写问题
- 适度扩大检索范围
- 再生成一次最终回答

### 6.1.8 返回前端并更新会话

回答完成后：

- 普通接口返回 `answer + references + source_badge + 元信息`
- 流式接口先输出 token，再输出 `meta` 和 `done`
- 后端把本轮用户问题与最终回答写回会话记忆
- 前端渲染答案、来源标签、本地证据摘要与运行状态

## 15. 当前运行时保护

为适配 2 核 2G 的部署条件，当前版本已经加入最小运行时保护：

- 上传灌库互斥：同一时刻只允许一个上传灌库请求进入
- 聊天轻量限流：同一进程内仅允许少量聊天请求并发执行
- 超限快速失败：避免请求堆积后把整体服务拖慢

当前行为约定如下：

- 当上传灌库正在执行时，新的上传请求返回 `409`
- 当聊天容量已满时，新的聊天请求返回 `429`
- 流式聊天在响应结束后自动释放并发槽位

这部分保护的目标不是高并发扩展，而是保证“小机器上仍然稳定可用”。

- `detail`
- `error.code`
- `error.message`
- `error.retryable`
- `error.status_code`

这保证了：

- 简单客户端仍可只读 `detail`
- 正式前端可以按 `error.code` 做稳定分支处理
